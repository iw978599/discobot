# The interface: narrow screens, touch, the keyboard, the mixer, Help

Part of `AGENTS.md`, moved here to keep that file small. Read it before changing the layout, a phone or tablet, touch, keyboard focus and Tab stops, the bar of units, knobs and faders, the on-screen keyboard, the piano roll, the mixer, the walkthrough, Help, or the lane editor's tabs, and keep it up to date as you would `AGENTS.md`.

- A Kindle or Fire tablet (Silk) is given the phone layout by its viewport width: an inline script in `ui/index.html` sets `width=640` on the viewport tag when the user agent matches `KINDLE_PATTERN` in `ui/src/services/kindle.ts` (a test keeps the two expressions the same). The layout rules themselves are unchanged; do not add a second way to choose the layout. Not verified on a real Kindle.
- A step row and a drum row carry `--bar` and `--across` inline, and the phone block reads them: eight steps to a row, or six where the beats are six steps, so a row ends on a beat. A guest is told beats (quarter notes) and never the signature. Kids mode, the starting beats and the sample song are 4/4.
- `.rack-page` is the page's scrolling area (the window itself does not scroll), which is what lets the transport unit be `position: sticky`. Keep the page's top padding at zero, or scrolled content shows above the bar.
- At 720px wide and under, one block at the end of `rack.css` rearranges the rack for a phone: units stack their parts, the step grids go eight to a row (`.step-row` sets its columns inline, so that rule needs its `!important`), menus rise from the bottom, dialogs fill the screen, and safe-area insets are respected. It is the same components and the same markup; add narrow-screen rules there and nowhere else. `phone-layout.spec.ts` checks it, and that a wide screen is untouched.
- A phone on its side is wider than 720px and very short, and gets the same arrangement: the block's condition, and `useNarrow`, also match a screen up to 960px wide and 500px tall that is wider than it is tall. Keep the two the same. A second, smaller block after it gives height back on that screen (a lower bar of units, sixteen steps in a row, the piano roll's heading on one line). `Walkthrough` still places its card by width alone.
- On a narrow screen the top bar is one line that never wraps and never scrolls away: the tempo, Play, Undo and Redo as drawn arrows (from 375px wide; narrower, they are in the sheet), and a button named "More controls". `TransportUnit` has two arrangements, chosen by `useNarrow`, built from the same pieces: each control is written once, as a constant, and placed on the wide bar or in the sheet. The wide arrangement's markup is what it was before the sheet existed; keep it so. The old `--transport-tuck` measuring is gone.
- The sheet is a `Dialog` with `sheet`, rendered inside the `header` (so `.transport` still holds its controls, and the bar's layer puts it over the bar of units). It holds the project's name and save state, Tap, Click and Count, Mute and Volume, and a row each for Project, Export, the account, MIDI and Help with a line saying what it is for. A switch (Mute, Click, Count, Tap, Volume) leaves the sheet up. Anything that opens a dialog or leaves the page goes through `leaving`, which puts the sheet away in the same turn: the sheet hands focus back to its button as it unmounts, the new dialog then records that button as where focus came from, and so closing the dialog returns the keyboard to "More controls". Do not open a dialog from the sheet any other way. The Volume knob's own sheet (`KnobSheet`) is the one thing that opens over it.
- A `Dialog` leaves Escape alone while a `[role="menu"]` is open inside it, so the Project menu in the sheet closes first and the sheet on the next press.
- Project → Start Live Session opens setup for the current project, through the same `leaving` path on a phone. It offers Account when signed out, explicitly adds a browser-only project to the account, and reuses Projects' `Sharing` controls. Invitations sync first and stop if the open project changes (including a conflict fork), storage is paused or a save fails. Access lasts beyond the session; only the owner manages it. Collaborators sign in and choose Project → All Projects → Shared with you → Open (Account → Sync Now refreshes offers). Share Link is still separate. Setup never opens a second room: shared projects connect automatically, and the rack now shows connecting, waiting alone and unavailable states as well as participants. A closed connection can be retried without replacing a running one; WebSocket failures cannot distinguish an older server from a lost connection.
- The app's name is an `h1` for a screen reader only on a narrow screen (`sr-only`). A browser test can see it but cannot press it.
- `useTapTempo` (in `HeaderParts.tsx`) holds the taps, the Shift+T key and the display's flash; it is apart from `TempoDisplay` because a narrow screen puts the Tap button in the sheet. `TempoDisplay` draws the Tap button only when it is handed `onTap`.
- `useWakeLock` keeps the screen on while anything is playing, where the browser allows it.
- A narrow screen shows one unit of the rack at a time, chosen from the bar along its bottom (`UnitBar`, rendered only when `useNarrow` says the screen is narrow). Which unit is view state in `Rack`, remembered per browser by `services/rackView.ts` and never in `useStudio`. `Rack` puts it on `.rack` as `data-shown`, every unit carries a fixed `data-unit`, and the phone block of `rack.css` hides the units that do not match. The units are not told which is on show, so none renders for a switch.
- A unit that is off screen is hidden with CSS and never unmounted. Its audio, its scheduler lane and its MIDI go on; its step lights go on being switched, so they are right when it is shown; and a guest's frame is the same frame, still sending sound. Do not turn this into conditional rendering: a guest would reload and lose what it was doing. All the guests are one unit (`guests`), and the bar offers it only when the project has one.
- The mixer (`MixerModule`, between the drums and the effects, `data-unit="mixer"`, on the bar as "Show Mixer") stores nothing and makes no sound of its own. The owner's word on 2026-10-13 was "a new unit, same levels. Each instrument should have a channel": every control on it is a second view of one that is already in a unit (a lane's level and pan, mute and solo; each drum's volume, pan, mute and solo; the drum master; a guest's level and mute; the two effect returns and the two aux returns; this browser's volume), read from the same state and changed through the same handler, so the two always agree and undo treats them alike. Never give the mixer a value of its own, a handler of its own or a place in the project. The one thing done from it that is not a level is putting the lanes in another order, by dragging a strip by its name (`useDragOrder` with a handle, `.mixer-name`, so a fader is never dragged); that is the project's lane order, which the rack follows too. It has no level meters: nothing in the audio layer measures a level, and one must not be drawn that does not. The one thing on it that reads the audio is the picture of the whole mix beside the main volume (below).
- A picture of the sound (`Scope` in `ui/src/components/Scope.tsx`, roadmap 21): a canvas showing a wave or a spectrum, at the top of the open lane's Sound level and on the mixer beside the main volume. It reads an `AnalyserNode` that the engine makes only when a picture first asks (`analyser()` on a lane from `createLane`, after its level and inserts and beside its sends; `AudioEngine.analyser()` after the safety shaper), which feeds nothing, so the sound and exports are unchanged. Before there is an audio context the engine returns none rather than making one, so a picture never starts audio before a click. It draws from its own animation frames, never React state, and only while it is on screen (an `IntersectionObserver`, and not in a hidden tab), and asks for its analyser every frame since a lane's audio is made when it first sounds. It writes how much it shows to `data-peak` for the browser test. It is not a meter.
- The mixer does not read the studio's lanes or drums, which are new objects after every note and step. `Rack` gathers what it shows with `mixerChannels` and hands it the same object until one of those levels changes (`sameMixer`), so it renders for a level, a pan, a mute or a model's name and for nothing else; `rack-renders.spec.ts` counts it. A level that comes to be shown on the mixer is added to `mixerChannels`, never read from the studio inside `MixerModule`.
- Every control on the mixer is named "Mixer …" ("Mixer Synth 1 level", "Mixer Kick volume", "Mixer Kick mute", "Mixer Drums master volume", "Mixer Synth return", "Mixer main volume", "Mixer guest <name> level"), because the specs find the controls it mirrors by their exact names. A pan reads as its own knob reads it, a lane's to 100 either side and a drum's to 50 (`panText`). The strips can be folded away with Hide, remembered per browser (`storedMixerHidden` in `rackView.ts`).
- `Fader` is `useKnobInteraction` with another drawing: the drag, the wheel, the arrow keys, the middle click back to its default, the figure typed under it and the sheet a finger's tap opens are the knob's own. The hook's last argument, `travel`, is how many pixels of drag cross the whole range; a fader passes its slot's travel (`FADER_TRAVEL`, which `Fader.css` must agree with) so the cap stays under the pointer, and a knob leaves it at 150.
- With the mixer the bar of units has nine switches when the project has a guest. On a phone 360px wide each is then 39px wide, the one case under 44; `phone-layout.spec.ts` holds that they still fit without the bar being slid.
- The guests unit is the one unit not hidden with `display: none`. A page in a frame that is not rendered has its animation frames stopped and may have its timers slowed, and measures itself as nothing. So a guest that is not on show keeps its size, fixed to the top of the screen and clipped to nothing, with `pointer-events: none`; `Rack` sets `inert` and `aria-hidden` on it from a layout effect, since the unit itself is not told. `docs/GUEST_PROTOCOL.md` says what a guest may assume. Do not "simplify" this to `display: none` or `visibility: hidden`.
- The lane on show and the open lane (`studio.selectedSynthId`) are kept the same by one effect in `Rack`: if the open lane changed, the view turns to it; otherwise the view's lane is opened. A lane on show that was not open would have no editor, keyboard or piano roll. The walkthrough puts back the unit and the open lane it started from when it ends.
- A browser spec that uses something a phone keeps in the top bar's sheet calls `more(page)` first, a small helper repeated in each spec that needs it, which raises the sheet at phone width and does nothing on a wide screen; `less(page)` puts the sheet away after something that leaves it up (a switch, or a look at the project's name). The sheet cannot be raised from under an open dialog, so a check of the bar made while a dialog is open is skipped at phone width (`onPhone`).
- "All" on the bar is the whole rack on one page, the first phone arrangement. The browser tests at phone width start with it remembered (`storageState` in `playwright.config.ts`), because they were written for a rack with everything on the page; only `phone-layout.spec.ts` forgets it and checks the paging. A new spec that depends on the paged layout must forget it the same way (`paged` in that spec).
- The lamps on that bar are not about which unit is on show (that is the lit line along the top of its switch). A synth lane's lamp and the drums' light on each step that unit sounds, and only those two kinds of unit have a lamp; the others have an empty place where it would be. `UnitBar` switches the class `lit` on the lamps itself from the playhead, the way the step lights are switched: one layout effect with no dependency list, and `lit` must never be in a lamp's `className`. `services/unitActivity.ts` says whether a lane or the drums sound on a step (mutes and solos counted, chance not). A muted unit has `data-muted` on its switch, a hollow lamp and its name struck through; the drums count as muted when every drum is.
- A switch on the bar that is held for `TAP_HOLD_MS` mutes or unmutes its lane, or all the drums (`handleDrumMuteAll`), without showing it; Shift+M on a focused switch does the same. A tap still shows the unit: the click that follows a hold made with a mouse is swallowed (`held`). A phone may answer a held finger with `contextmenu` before the timer is up, and that is taken as the same hold. Guests, the song and the effects have nothing to mute. The hint for this is in the top bar's sheet and in Help, since a hold cannot be discovered.
- A switch on the bar moves keyboard focus into the unit it shows (the unit is given `tabindex="-1"` at that moment, not in its markup) and scrolls the page back to its top, so the unit starts under the transport. The bar's switches are named "Show …" so they are never mistaken for a lane's own name plate, which is a button called "Synth 1".
- A knob (`Knob`, `DrumKnob`) that is tapped with a finger or a pen opens `KnobSheet`: a `Dialog` docked to the bottom edge (`sheet`) with the value in large figures, a native range slider and a step button either side. It is the knob's own value, limits, step and handler; do not give it a second copy of any of them. A mouse never opens it, so a desktop is as it was. The sheet is put on `.rack-page` with a portal, so it lies over the rack from inside any unit and still has the rack's colours.
- `useKnobInteraction` decides what a touch is. A finger that moves less than `TAP_SLOP` is a tap and turns nothing; further, it is the same drag a mouse makes. The tap is acted on at its `click`, not when the finger lifts: opened any earlier, the sheet would be under the finger in time to receive that click. A tap does not always end in a click (the browser check saw a touch on a drum knob that ended with `pointerup` and nothing after), so it is also acted on `TAP_WAIT_MS` after the finger lifts if no click has come. Keep both.
- The scroll wheel turns a knob (`knobWheel.ts`, wired in by `useKnobInteraction`'s `ref`, so `Knob`, `DrumKnob` and the effects panel's knobs all have it). The listener is native because React's is passive and could not stop the page scrolling. A wheel event is the page's unless the pointer (a mouse) has rested on the knob `WHEEL_REST_MS` (the knob then has `data-wheel="ready"`) and the page was not being wheel-scrolled in the `WHEEL_GAP_MS` before; once a knob is turning, it keeps the wheel while events come within that gap. A notch is 2% of the range, at least one step; Shift is one step; one event never counts for more than one notch, and small trackpad events add up. A run of notches is one undo entry because the store makes a run of changes to one control one step while each comes within `UNDO_GAP_MS` (300 ms) of the last. The rest rule is a choice the roadmap left to the builder and the owner has not confirmed it. `knob-wheel.spec.ts` checks it; a test must wait for `data-wheel="ready"` before wheeling.
- A press of a mouse's middle button on a knob puts it back at its default (`useKnobInteraction`, so every knob has it): the knob's `defaultValue`, which every `Knob` and `DrumKnob` in the app is given, read from where that default is already kept (`createDefaultSynthParameters()` for a sound, `EFFECTS_DEFAULT`, `DRUM_FX_DEFAULT`, `CHORUS_DEFAULT` and `EQ_DEFAULT` in `effectSettings.ts`, `DRUM_SETTINGS_DEFAULT` in `drumKits.ts`). The owner chose default over zero on 2026-10-13. It is the default of a new sound, not of the preset the lane has loaded. A new knob must be given its `defaultValue`; without one a middle click puts it at zero. It is one change through the knob's own handler, so one undo entry. `knob-wheel.spec.ts` checks it.
- A knob's hint (`tooltip`, `title`) is shown in its sheet, since a phone has no hover. Do not put anything a person needs only in a `title`.
- The on-screen keyboard tracks each finger on its own (`pointers` in `Keyboard.tsx`: pointer id to the note under it). A note stops when the last finger on its key leaves, so releasing goes through `leave`, never straight to `handleNoteUp`. A finger or pen that moves plays the key under it, looked up with `elementFromPoint` because its events keep arriving at the key it first pressed; a mouse holds the key it pressed, and with Hold on nothing slides. A key's `blur` lets go only if no finger is on it: a second finger takes the focus from the first one's key.
- A key held by a finger is also let go when the strip of keys changes width (a `ResizeObserver` in `Keyboard`). That is the only thing that says the lane's unit was switched away on the bar, since a hidden unit is not unmounted and no pointer event is sent, and it covers the phone being turned. Notes latched with Hold are left sounding, as they are when the page is scrolled away from them.
- On a narrow screen the keyboard is a strip of three octaves that shows one (two on a phone on its side), moved an octave at a time by the Lower keys and Higher keys buttons, which `Keyboard` renders only when the strip is wider than its box. The strip has `overflow: hidden`: it is moved by those buttons and by focus, never by a finger, because a finger that moves is playing.
- The on-screen keys are one stop for the Tab key (a roving `tabIndex`, as the grids of steps have): the key the keyboard was last on while its octave is on show, or else the first key on show, so Tab never lands on a key that is out of sight. `services/keyboardKeys.ts` says where a key goes: up and down move a semitone along the keys (up is the higher note), so the black keys are reached, and Home and End go to the two ends. Left and right do the same only while no step is selected on the lane; with one selected they are left for the `window` listener in `SynthModule` that walks the selection, as before (`arrowsWalk`, which `KeyboardPanel` works out from `selectedStep`). The owner has not confirmed that rule. The handler calls `preventDefault` for a key it takes even at the last key, which is what keeps the page from scrolling and that listener from acting. Space and Enter play the key as before, and the letters of the computer keyboard are untouched. The key that has the focus is the stop wherever the strip is (`keysFocused`), and `reveal` says where the strip is going as well as moving it: the scroll is heard a frame later, and in that frame the stop was another key, so Tab pressed straight after Home or End went to a key instead of leaving them. The check on GitHub passed only on a retry because of it.
- A key that takes the focus is brought on show by `reveal`, a whole octave at a time (`octaveOnShow`), from the key's own `onFocus`. The arrow keys focus with `preventScroll`, because the browser's own scroll would leave the strip part of the way along an octave, which the strip never is.
- The piano roll on a narrow screen has every step of the bar in the page, as it does on a wide one, in a grid that shows some of them: `PianoRoll` counts how many fit at 44px or more (`ACROSS`), hands the count to the stylesheet as `--roll-fit`, and the Earlier steps and Later steps buttons move the grid's `scrollLeft` a beat at a time. Nothing is taken out of the page or hidden with `display`, so the playhead light, the arrow keys and every browser test that clicks a cell work as before. Which steps are on show is read back from the grid's scroll position, not kept as a second truth; keep it in the component.
- The roll's grid is never moved while a pointer is down on it (`pressing`): a step selected from the row of steps is brought on show, one selected by pressing a cell or a handle is not. Do not answer the grid's own `scroll` event by moving it either: a browser test's click scrolls a cell into view first, and a grid that then snapped would put a different cell under the click.
- Only the note names slide the roll, and only up and down: the cells have `touch-action: none`, so a finger on a cell is always editing and the page cannot scroll under it. It starts at its lowest octave, the one the octave setting names, whenever it is shown or the octave changes.
- The roll is a `role="grid"` to a screen reader: a `row` for the step numbers and one for each note, the step numbers `columnheader`s named "Step 1" (the corner over the note names is one too, named "Note"), each note name a `rowheader`, and each cell's button inside a `gridcell`. The rows and the `gridcell` wrappers are `display: contents` (`.piano-roll-row`, `.piano-roll-slot`), so they have no boxes and the layout is still the one CSS grid of headers and buttons. A cell is still a button named like "C3 step 1" with `aria-pressed`; do not move the role onto the button, which would take both away. Nothing may look for the grid's parts by `firstElementChild` or `parentElement` any more: find the corner by `.piano-roll-corner` and a cell from `gridRef`.
- What a finger does on the roll: on an empty cell it adds the note as it lands, as a mouse does, and paints if it moves. On a note that is already there it waits: lifted within `TAP_HOLD_MS` the note is taken out, moved further than `TAP_SLOP` it rubs out along its way, and held still it keeps the note and only selects its step. So a held finger changes nothing, the rule the knobs have, and the two constants are the knobs' own (`useKnobInteraction`). A mouse still acts at once on any cell; `controls.spec.ts` pins that a touch on an empty cell does too.
- A note's length handle is 20px wide on a narrow screen, under half of the narrowest cell, so the middle of a note is the note. A finger's drag on it is captured by the grid: the handle is unmounted as the note grows, and a finger's events would otherwise still be addressed to it. A finger that lands on the handle of a note one step long and lifts within `TAP_HOLD_MS` without moving `TAP_SLOP` was tapping the note, and takes it out (`tap` in `resizing`). Do not give the handle an `onClick`: React then marks it as something to click, and a browser steers a touch that lands near such a thing onto it, so a finger on the middle of a note was handed to the handle. The same goes for any small thing laid over a control a finger uses.
- A row of steps, the drum grid and the piano roll are each one stop for the Tab key (a roving `tabIndex`): the selected step, or the cell the keyboard was last on. `gridKeyTarget` in `rack/gridKeys.ts` says where an arrow key, Home or End goes in the step row and the drum grid, reading how many cells are on a line from where they are, so it is right at eight to a row. The on-screen keys are a fourth such stop, described with the keyboard above. In a lane's row the arrow keys move the keyboard only while no step is selected; once one is, left and right walk the selection as before (the `window` listener in `SynthModule`, which the row stands aside for through `arrowsWalk`). The grid's handler calls `preventDefault`, which is what stops that listener walking a lane's selection for an arrow pressed in the drum grid.
- On a screen showing one unit, the walkthrough turns to the unit each stop is in (`onUnit`), found from the stop's selector by its nearest `data-unit`. A stop's part must stay inside the unit it belongs to.
- On a narrow screen the walkthrough's stops about Project and Export, the account and Help light the "More controls" button and say the thing is under it (`stopsFor(signedIn, narrow)`); it does not raise the sheet, which is a dialog of its own. The number of stops is the same at both widths. A new control that goes in the sheet and has a stop needs both wordings.
- The walkthrough (`Walkthrough.tsx`) is the one overlay that is not a `Dialog`: it lights one part of the rack and puts a card beside it, or along the bottom of a narrow screen. Its card is `aria-modal`, which is what makes the piano keys and the step arrow keys stand down while it is up. It finds each stop by a selector in `STOPS`; renaming one of those classes or labels means changing the stop and `walkthrough.spec.ts` with it. A stop whose part is not on the page shows its card alone.
- The walkthrough starts by itself only after the recovery code of a new account, and only in a browser that has not had it (`walkthroughSeen`); Show the Walkthrough, in the account dialog and in Help, starts it at any time, signed in or not. Browser tests that sign up set `discobot_walkthrough_v1` first unless the walkthrough is what they test.
- Help (`HelpModal` in `rack/HeaderParts.tsx`) is written as `<section>`s, each with an `id` and an `h3`. Its list of headings and what its search box looks through are both read from those sections when it opens, so a new section needs only an `id` and a heading, and nothing else lists them. `matchHelp` in `services/helpSearch.ts` decides what a search leaves: every word typed, anywhere in the section. A section that does not match is hidden with `hidden`, not taken out, or its words would be gone from the next search. A heading in the list moves focus to the section's `h3`, which is not a Tab stop; the `h3` sends Tab back to the list itself, because `Dialog` only keeps Tab in from its first and last control. `help-search.spec.ts` holds the headings and what a few words find; change it with the Help text.
- Each unit has a "?" on its name plate (`UnitHelp`, in `ui/src/rack/UnitHelp.tsx`) that opens Help at the section about it; `UNIT_HELP` there says which section is which unit's. Whether Help is open is still `studio.helpOpen`; the section to open at (`helpAt`) is view state in `Rack`, set by `openHelpAt` and forgotten whenever `helpOpen` goes false, so Help from the top bar always starts at the top. `openHelpAt` is the same function on every render, because it is a prop of the `tracked` units and of the effects panel, which is a `memo`. `HelpContent` jumps to the section in a mount effect, which runs after the `Dialog`'s own because the dialog is its child.
- The "?" is `position: absolute` in the top corner of its plate, so no plate is taller for it; a plate that has one carries `helped`. A lane's plate is itself a button and cannot hold another, so the two stand in `.rack-plate-box`, which takes the plate's place in the row. On a narrow screen the button is 36px and the plate keeps 44px clear for it at its end. Its name is "Help for …", and the top bar's is exactly "Help": a test must ask for either with `exact`.
- A new section of Help needs its name in `HEADINGS` in `help-search.spec.ts`, and must not use a word that spec searches for (kick, unison, import) unless it should be found.
- The open lane's editor (`SynthControls`) has two levels, each a `tablist`: "Synth editor" holds Notes and Sound, and under Sound "Sound pages" holds Osc, Filter, Amp, LFO, Arp and Sends. Notes is the step tools and the keyboard or piano roll and nothing else. Sound is the model, the preset menu and its tools (name, Save, Delete, Import, Export), then the pages. Hold and Remove are on the levels' own line, which is the same on both levels so that going from one to the other moves nothing above what opens. Which is open is still the one `tab` state in `SynthModule` (`SynthTab`: `notes` is the Notes level, anything else is that page of Sound), so it is each lane's own, lasts for the visit, starts on Notes and is never in `useStudio` or the project. `SynthControls` remembers the page Sound was last on (`soundTab`). What is not on the open level is not rendered, as a page that was not open never was: do not keep anything there that a person would lose (the preset's name on its button is state of `SynthControls`, which stays).
- In both rows the open tab is the one Tab stop and the arrow keys, Home and End move to a tab and open it (`tabKeys`). A browser spec reaches a page of the sound by pressing Sound first: the specs' `tab(page, name)` helpers do it, and `openPresetGroup` does it for the presets. A spec that then needs the keyboard or the piano roll presses Notes again.
- Each lane shows four knobs plus Level. For a synth model with macros those four are the macros; otherwise Cutoff, Reso, Env and Decay.
- The computer keyboard plays notes with unmodified letter keys (matched by physical position, `event.code`). Any new single-key shortcut must use a modifier; tap tempo is Shift+T for that reason. The one exception is Space, which plays and stops like Play All (`TransportUnit`). It stands aside whenever `spaceBelongsToTarget` says the focused element uses Space itself (a button, link, field, select, menu item) and while any `aria-modal` dialog is open, so a focused button is still pressed by it.
