# Discobot — AI Context / Restore Prompt

## Project Overview
Browser synth/sequencer/drum workstation with three npm workspaces. All project
operations, synthesis and playback run locally in the browser, signed in or not.
Accounts are optional and live in a small separate API (`server/`); the app never
depends on it.

## Architecture
```
discobot/
├── engine/    # Browser-compatible TypeScript DSP and shared types
├── ui/        # React/Vite UI, Web Audio and local project/sample services
└── server/    # Accounts API: a Cloudflare Worker with a D1 database
```

### Audio Flow
Browser audio-clock transport → local synth/drum generation → Web Audio effects
and output. Project edits/named patterns use localStorage; sample bytes and
metadata use IndexedDB. These stores are origin scoped and are not cloud backups.

### Current Services
- `ui/src/services/localService.ts`: in-process project operations/events and persistence.
- `ui/src/services/browserTransport.ts`: audio-clock look-ahead scheduling.
- `ui/src/services/sampleStore.ts`: IndexedDB sample persistence.
- `ui/src/services/wavExport.ts`: local offline rendering and WAV download.

Use Node.js 22+, `npm ci`, `npm run dev` and
`http://localhost:3000/discobot/`. Build with `npm run build`; `npm start`
previews the static output at `http://localhost:4173/discobot/`.

Resume Web Audio through a user gesture. Web MIDI hardware support is optional;
unsupported/permission-denied input must not block the keyboard or MIDI files.
Automated checks do not establish subjective audio quality or real MIDI hardware
compatibility. See `README.md` and `docs/CONTROL_AUDIT.md`.

## Behaviour Worth Knowing
- A Kindle or Fire tablet (Silk) is given the phone layout by its viewport width: an inline script in `ui/index.html` sets `width=640` on the viewport tag when the user agent matches `KINDLE_PATTERN` in `ui/src/services/kindle.ts` (a test keeps the two expressions the same). The layout rules themselves are unchanged; do not add a second way to choose the layout. Not verified on a real Kindle.
- There are many projects. `localService` holds the open one, with a working copy in `localStorage` (written synchronously, so it survives a closing tab) and a record in the library that is updated after every write. Switching projects goes through `stash()` then `activate()`, which emits `init`. Project operations are async methods on `localService` (`newProject`, `openProject`, `copyProject`, `renameProject`, `deleteProject`, `importProject`), not operations.
- Each project keeps up to 20 earlier versions in the library (`keepVersion` in `localService.ts`): one when it is opened, one every five minutes of editing, and one before anything replaces it (a sync download, a restore). A version identical to the last one kept is skipped, compared in `normalized()` form. Anything new that overwrites a project must call `keepVersion` first.
- Versions are in this browser only: not in project files, links or sync. Deleting a project deletes them.
- Importing a file or opening a share link always creates a new project; nothing overwrites an existing one. Project names are unique.
- A row in the Projects dialog can be a family: a project and the others the app named after it, with a list (`Version of <name>`) choosing which one the row's buttons act on. A family is worked out from names alone, in `projectFamilies.ts`: a name with every ending the app generates taken off (` copy`, ` (earlier version)`, ` (this browser's version)`, and the ` 2`, ` 3`… that `uniqueName` adds). The first three are constants there, and `localService` and `projectSync` build their names from them: a new generated ending belongs in that file too, or its projects get rows of their own. Nothing about a family is stored, and which member a row shows is the dialog's own state. A browser test that finds a project's row by name must use the family's name and pick the member from the list.
- `savedPatterns` only exists to migrate arrangements saved by older versions into projects (`openLibrary`). Do not add to it.
- Share links and project files are untrusted. Both go through `restore()`; `readProjectFile` does that without opening the project.
- A project has scenes (every lane's pattern plus the drum grid, each one or more bars) and a song (scenes in order, with repeats). The lanes' patterns and `drumState` steps in the store are always the open scene; its slot in `scenes` is only brought up to date by `commitScene()`, which runs before anything reads `scenes`. Never read a scene's stored copy for the open scene: use the live pattern.
- Sounds, kit settings, tempo and effects are project-wide. A scene holds steps, and which lanes and drums are muted or soloed (`scene.mutes`): `captureScene` records them and `applyScene` puts them back on the lanes and the drum state, so everything else still reads `muted` and `solo` where it always did. A scene saved before this holds none and leaves the lanes as they are.
- A song export applies each scene's mutes bar by bar (`applySceneMutes` empties the silent lanes, `sceneDrumState` carries the drum flags) and then hands the lanes to the exporter unmuted. Never filter a song export by the open scene's mutes.
- In song mode the scheduler picks the scene from the transport's bar number (`sceneAtBar`), plays any scene other than the open one from its stored copy, and asks the store to open the playing scene with `localService.selectScene`, a plain call. It emits synchronously, and the `sceneChanged` handler updates the refs the scheduler reads straight away; keep both true or a bar would play the wrong scene.
- Every edit inside a project is a typed operation (`docs/TYPED_STORE_PLAN.md`, done). An edit is an `Operation` handed to `localService.apply`, usually through a one-line typed helper such as `setDrumSwing`. `apply` is synchronous and must never be `async`: the event has been delivered before it returns. It answers `{ ok, value }` or `{ ok: false, status, error }` and does not throw for a refusal; it throws only before the project is initialized. `reducers` has one reducer for every operation, and the compiler fails if one is missing. Reads are `getScenes`, `getTempo`, `getDrumKits` and `snapshot()`. Several edits that must land together go in one `applyAll`.
- Reducers (`projectReducers.ts`) only change the state they are handed and say what to save and send. They never emit, save or read the clock; `apply` does the first two and `write()` stamps the time. `useStudio` does not set its own state before calling a typed helper: the event is the one place a value is applied, and it carries the value as the store kept it (a drum master volume is held to 0 to 1). `storeEdits.test.ts` pins what each operation answers, emits and saves, and `storeOps.test.ts` holds each typed helper to it.
- What is in an operation is the caller's own objects, not the fresh parse of JSON a route's body was. A reducer never keeps one in the project as it is, and reads an object in an operation (a patch, a whole state) only through `sent` in `projectReducers.ts`, which is that trip through JSON: without it a key that is `undefined` counts as sent, and `{ state: undefined }` deleted a guest's settings. A reducer also refuses an id it is handed that is malformed or taken.
- A lane's sound reaches the audio in one place: the `synthUpdate` case of `useStudio`'s message switch, which calls `synthAudio.updateParameters`. A knob, a macro, a preset, undo and Reset all get there by calling `localService.setSynthParams`; apart from a project being opened and the last step of Reset, nothing else sets `synthParams` on a lane, and nothing new should. A lane's octave and keyboard (`setSynthPrefs`) are saved without an event, so they alone are still set on the lane by the handler that changes them.
- The drums on screen are set in one place, the `drumFullState` and `drumKitChanged` cases of `useStudio`'s message switch, which also write `drumStateRef` so the scheduler and a handler making a second edit before React has rendered see the first. A drum handler never calls `setDrumState` itself.
- A lane's pattern is written only through `localService.writePattern` and set on screen only by the `patternCreated` and `patternUpdated` cases of `useStudio`'s message switch, which also move `synthsRef` (`commitPattern`), so a handler making a second edit before React has rendered, such as the next painted cell, builds on the first. A handler still sets what the event cannot carry (`selectedStep`, `stepRecordPointer`, the playhead).
- The starting-points strip also offers Sample Song (`sampleSong.ts`): a whole song built as a project file from the open project's file (for its shape, kit and effects) and three built-in presets, and opened through `handleImportProject`, so it is a new project and nothing is overwritten or needs undoing. Its sounds are named by preset id (`SAMPLE_SONG_SOUNDS`): renaming or removing one of those presets breaks it, and a test says so. A starting beat still changes no sound; it sets each hit's strength (`velocities`) as well as where the hits are, and a few hits' chance and repeats (`chances`, `repeats`). `starterDrums` writes a drum's chances and repeats whenever the grid already holds some, so those of a beat tried before do not stay under the next; keep that if a beat is given anything else per step.
- A synth lane can swing (`swing` on the lane, the `synth.swing` operation, the Swing button beside Bars): it then plays every second sixteenth late by the drums' swing, as the drums are. It is a switch and not an amount of its own so that one knob sets the groove; that was the builder's choice (roadmap V11) and the owner has not confirmed it. Stored only while on, so a project that never swung is unchanged in storage, hash and sound. `swingLate` in `drumScheduling.ts` is the one place the delay is worked out, for the scheduler, `renderSynthBars` (its last argument) and MIDI export; anything else that times a lane's notes must ask it too. The notes, their MIDI out and the step light move; a step's automation stays on the step, live and in export alike. A recorded note is still written on the grid.
- The arpeggiator's Range (`arpeggiator.octaves`, 1 to 3) is how many octaves it runs through, for a note and for a chord alike. Absent is Auto, which is what it did before there was a choice, and the control sends 0 for it so the store's merge does not keep the old value.
- An arpeggiator given one note plays that note and the two octaves above it (`ARP_PATTERNS`); given a chord it plays the chord's own notes. Until 2026-10-13 one note gave a major chord, so a project saved before then with the arpeggiator on single notes now plays octaves. The owner asked for the change after people using the app reported it.
- A project that is opened with one scene, no note and no drum hit shows the starting-points strip above the song unit (`showStarters`, decided each time a project is put on the rack). Choosing one sets the tempo, the drum grid and Synth 1's pattern as one undo step and changes no sound. The strip leaves only by its own Hide button: never take it, or any other unit, away because of an edit made below it, which would move the rack under the pointer that made the edit. Most browser tests start on an empty project, so the strip is on screen in them.
- Copy bar (`CopyBar`, shown beside the bar buttons of a lane or the drum grid that is longer than one bar) lays the bar on show over another bar of the same pattern, or over every other. It is an edit to the open scene, so it is one undo step and does not ask. A lane's goes through `writePattern` (`handleCopyLaneBar`); the drums' is the `drum.copyBar` operation, which takes every drum's steps with their velocities, chances and repeats. `barTargets` and `copyBar` in `patternLength.ts` hold the rule for both. Its wrapper carries the class `copy-to` as well, for the menu's placing: a test that looks for Copy to by that class must also ask for the button's name.
- Copy to (`CopyToScene`, the `scene.copyPart` operation) puts one lane's notes or one drum's row from the open scene into another scene's stored copy. Undo takes it back like any other edit; the control still asks before replacing something, because what it replaces is out of sight. A lane brings its own length; a drum row is laid along the other scene's grid, repeating or stopping short, and brings its velocities, chances and repeats with it.
- The song's order can be shown two ways, chosen in the song unit and kept per browser (`songView.ts`, like `rackView.ts`): the blocks, which are the default, and the playlist (`SongPlaylist.tsx`), a row for each entry with its bars, when it starts and how long it lasts. Both edit the same `song.entries` through `handleSongChange` and neither holds anything of its own; the playlist's rows come from `songRows` and its edits from `moveSongEntry`, `removeSongEntry`, `insertSongEntry` and `repeatSongEntry` in `songPlayback.ts`, which also say where the marked starting entry is afterwards. An edit arrives a moment after its button is pressed, so the playlist moves keyboard focus to the row that was edited once the new entries are in (`focusNext`). The playlist wraps its rows and has no rules in the phone block. Browser tests other than `song-playlist.spec.ts` are written for the blocks.
- A scene can carry a colour (`scene.color`, one of the names in `sceneColors.ts`, absent for none), drawn as a band on its chip, on its blocks in the song and on the share page. `commitScene` rebuilds the open scene from the live lanes, so it hands the colour back to `captureScene`; anything else added to a scene that is not steps or mutes must be carried the same way, or the first edit loses it. A scene made with + Copy or + Empty takes the first colour no scene has; the scene a project starts with has none.
- A built-in preset for a synth model is made from that model's four macros (`model()` in `builtInPresets.ts`), plus only what the macros leave alone (level, sends, spread, unison, the second LFO). Loading a preset puts its own values on the lane last, so one written by hand for a model would disagree with the knobs the lane shows and jump when one is turned. A test checks each agrees.
- A built-in FM preset that is brighter for a harder note has a low `fm.index` and a route from velocity to `fmIndex` that brings it back up: the route adds its depth times the note's strength, so the index a preset is heard at is the two together. `measureMotion` in `presetAudit.ts` says how far a held preset's level moves and how wide it is; `builtInPresets.test.ts` holds the presets that promise either to it.
- Each built-in preset's `gain` is set by measurement so that presets of a kind are about as loud as each other (`LEVEL` in `builtInPresets.test.ts`). Change a preset's sound and re-measure its gain; a lane's level cannot go above 2, which is why sounds made only of filtered noise sit a little under the rest.
- A synth model's macros set only part of a lane's sound, laid over what the lane has. There are two mappings. Turning a macro uses `mapSynthModelToEngineParams`: the macros alone, so a filter slope or a unison stack someone chose on that lane stays. Moving a lane to another model uses `enterSynthModel`, which also puts back what the model it leaves may have set and the new one does not set for itself: unison off, a 12 dB slope. A model that sets something no other model does must have it put back there, or it stays behind when the lane moves on (`mapModel` sets the first oscillator's level to 1 for the same reason). Moving to the plain engine puts nothing back: it is where a model's sound is taken to be changed by hand.
- A lane has insert effects of its own (`SynthParameters.inserts`: drive, tone, chorus, delay), run by `InsertChain` in `engine/src/synth/inserts.ts` at the end of `SynthCore.render`, so live playback and export are the same code and nothing about them is in the worklet wrapper or `wavExport.ts`. They come after the voices, the lane's level and pan, and before the lane reaches the mixer and its sends (the lane's level is therefore before the drive, so it changes how hard the drive works). `inserts` is absent from `createDefaultSynthParameters()` on purpose: absent means none, `sanitizeInserts` stores an effect only where it differs from `INSERT_DEFAULT` (`effectSettings.ts`), and a lane with none stores no key, so older projects load, hash and sound as before (and `SCHEMA` was not bumped). The core flattens them as `insDrive` to `insDelayFeedback` (`flatInserts` in `voiceParams.ts`), with a tempo-synced chorus rate and delay time worked out there from the tempo. The Inserts page sends the whole `inserts` object on every change, with `sync: 'off'` for none, because the store's merge keeps what is left out. A whole sound with no `inserts` (a preset, Reset, undo) clears them: `synth.params` treats a patch carrying `WHOLE_SOUND` and no `inserts` as none. The effects clear their buffers when all are off, so no echo comes back later. Not verified by ear.
- There are two aux buses (`EffectsLoopState.aux`, a list of two `AuxBus`: A then B), each pointed at an echo, the Hall or a chorus (`AuxKind`), with its own return `level`, a `main` and a `shape` setting whose meaning depends on the kind (`AUX_LIMITS` in `auxSettings.ts`: time and feedback, decay and damping, rate and depth) and a `sync` for the echo's time and the chorus's rate. The owner's word on 2026-10-13 was two buses and the effects the builder's choice. Every lane (`fxSends.auxA`, `auxB`), the drum kit (`drumFx.sends`) and each guest (`guest.sends`) has a send to each. All of it is optional and absent means as before: a send is stored only above nothing (`sanitizeSends`, `guestSends`), `aux` is stored only when a bus differs from the starting pair (`sanitizeAux`: an echo, then a Hall), and none is in the defaults passed to `localService`. A control that can bring a send back to nothing always sends it (`normalizeFxSends`), or the store's merge keeps the old value. `createAuxEffect` in `browserAudio.ts` builds the effect for live playback and for `connectEffects` in `wavExport.ts`; live, a bus's effect is built the first time a lane sends to it (`syncAux`) and swapped, with the old one let go, when its kind changes; in an export only a bus that is sent to and has a level is built. The buses come back through the group's return like the five shared effects, and `effectsTail` lengthens an export's tail only for a bus that is sent to. - Loops of native nodes, as Chrome renders them (a probe on the check machines, pull request 188): a loop is one render quantum (128 frames) longer than its delay, so a comb of 1000 frames rings at 1000, 2128, 3256 (this is true of the shared delay's repeats too), and a loop with two ways out, or two loops that feed each other, renders differently from run to run because the order a node's inputs are pulled in changes. The module's functions (`getAudioContext`, `createAudioLane`, `setEffectsLoop` and the rest) are one-line calls to it, and every caller still uses them: handing the engine to the hooks is not done yet. `dispose()` stops and disconnects all of it and closes the context; nothing in the app calls it, it is there for tests and for tearing down. An engine used after that makes a new context and keeps the settings it was given, as it does when the browser closes a context. The builders `wavExport.ts` uses (`createChorus`, `createMasterEq`, `createHallReverb`, `reverbImpulse`, `eqGains`, `chorusSweep`, `configureLimiter`, `scheduleDuck`, the curves) are plain functions and must not come to depend on the engine. A test makes an engine of its own by passing `new AudioEngine(...)` a function that returns a fake context (`audio-engine.test.ts`).
- Kick ducking is Web Audio gain automation, not core DSP: `scheduleDuck` in `browserAudio.ts` is called by the live scheduler and by `wavExport.ts`, so both pump identically. Export gets its kick times from `drumHits`, the same list the drum render uses.
- Each drum has a share of its own of the kit's delay send and reverb send (`DrumSettings.delaySend`, `reverbSend`, 0 to 1), set by the Delay and Reverb knobs under Sends in the drum strip. The owner's decision (2026-10-13): those two effects only, with the kit's own sends (`drumFx.sends`) as a master over them. What reaches the delay from a drum is the drum, times its share, times the kit's send. Absent means 1, all of it, which is what every drum sent before; `sanitizeDrums` stores a share only when it is under 1, so a project that never set one is unchanged in storage, in its hash for sync and in sound. The knob sends 1 and the checks drop it. A share cannot go above 1: a drum is kept out of an effect, never sent more than the kit.
- `DrumCore.process` takes two more places to write, and fills them with a second and a third mix of the same voices, each scaled by its drum's share where it is added to the kit's sum, so pan, level, choke, an imported sample and a recorded cymbal are alike in all three. With every share at 1 they are the kit sample for sample, and the kit is bit-identical whether or not they are asked for; `drumSends.test.ts` checks both. A share is read when a hit starts, as its volume and pan are. Live, the drum processor has three outputs and the drums' lane is made with `createAudioLane('drums', ['delay', 'reverb'])`: `taps` are inputs with the lane's volume and ducking whose only way on is the kit's send to that effect, and the kit's signal no longer feeds those two sends. In an export `renderDrumMixes` makes a mix only when a drum that plays has a share under 1, and `connectEffects` asks for it only when that effect is on and sent to; otherwise the graph is the one it always was. Drive, phaser and chorus are the whole kit's. A stem of the drums has its effects.
- A kit change with its defaults lays volume, tone, the second knob, tune, humanize and pan over each drum and leaves the shares, as it leaves the cymbal type; `drum.reset` clears them. Kids mode sends no shares, so its drums are what they were.
- Unison copies and the 24 dB second filter stage live in `SynthCore`. One unison voice and a 12 dB slope must stay bit-identical to the sound before they existed; a test checks it.
- A sound can have a second layer (`layer`): every note is then two voices, the second with its own share of the level, tuning, filter offset, slower attack and place from side to side. `startNote` gives a voice its `layer`, and everything the second layer does in `process` is behind `second` or `layered`, so one layer is bit-identical to the sound before there could be two; a test checks it. A layered lane plays four notes, not eight. `enterSynthModel` switches the layer off for every model but the CS-80.
- Two oscillators at one pitch are in fixed phase, and a pulse and a saw set that way partly cancel. Measure a model's level (`measurePreset`) before settling on its waves.
- The audio hooks return a stable object. Keep it that way: effects in `useStudio.tsx` depend on them.
- Octave shift range is -2 to +2 per lane and affects the on-screen keyboard, the piano roll range and the computer-keyboard piano.
- The metronome (`services/metronome.ts`, Click and Count on the transport) is this browser's setting, not the project's, and never in an export. `scheduleClick` in `browserAudio.ts` plays a click into the master level, past the lanes and effects. The count-in is in the scheduler, not the transport: `scheduleTick` clicks its bars and returns, and takes them off the bar number for everything after, so the song, the lanes and MIDI start count from where the music starts. Guests are told the first beat is after the count-in. An export that plays the arrangement through to record guests has no count-in and no click (`exportingRef`).
- The computer keyboard plays notes with unmodified letter keys (matched by physical position, `event.code`). Any new single-key shortcut must use a modifier; tap tempo is Shift+T for that reason. The one exception is Space, which plays and stops like Play All (`TransportUnit`). It stands aside whenever `spaceBelongsToTarget` says the focused element uses Space itself (a button, link, field, select, menu item) and while any `aria-modal` dialog is open, so a focused button is still pressed by it.
- Drum steps carry optional `stepProbabilities` and `stepRatchets` arrays next to `stepVelocities`. Anything that moves or copies drum steps must move all three.
- Exports must be repeatable: use `seededRandom` for anything random in WAV or MIDI export, never `Math.random`. That includes the reverb's noise (`reverbImpulse` takes a random source).
- A synth lane's third engine, beside analog and FM, plays an imported sample up and down the keyboard (`engine: 'sample'`, `sample: { id, root, loop }`). `SynthCore.setSample` holds the recording and the voice reads it in place of the oscillators, so the filter, envelopes, routes and second layer all apply, and live and export match. It comes the way a drum lane's does: `loadDrumSample`, kept per lane in `useStudio` (`synthSamplesRef`) for the worklet and for export (`synthSamples`). A lane with no recording, or one that is not on this device, plays its oscillators. The editor clears a sample by sending an empty id, because the store's merge would keep an id that was merely left out.
- A recording can begin part of the way in (`sample.start`) and go round a part of itself while Loop is on (`sample.loopStart`, `sample.loopEnd`), each a share of the recording from 0 to 1, so the same setting means the same place in whichever recording of a multi-note instrument a note plays. They are stored only where they are not the whole recording (the sanitizer drops a start of 0 and a loop of 0 to 1), so a sound that never set them is unchanged and its project's hash with it; `SynthCore` reads the whole recording for a loop too short to hold a sample. A sequence of waves has none of them. The last hundredth of a second of a chosen loop (less for a short loop, or one that starts near the beginning) is faded into what the recording has just before the loop's start, so the join does not click; a loop from the very beginning has nothing before it to fade into and goes round as it always did, which is what keeps the whole recording bit-identical.
- A recording played two or more times faster than it was made is read from a copy with its top octaves taken out (`halve` in `engine/src/dsp.ts`, the copies made once in `SynthCore.setSample` and kept by recording), or what the output cannot hold comes back as tones that were never in it. Within an octave above its pitch the recording is read as it is, which keeps every sound from before bit-identical and leaves up to an octave of that folding; closing that needs a copy for every half octave or a better reader. A voice changes copy only when its speed is plainly past the next octave (`sampleLevel`), so a vibrato across one does not flicker. Making the copies takes tens of milliseconds for a long recording, on the audio thread, at the moment a sample is set. A table of single cycles has no copies.
- `usedSampleIds` counts a synth lane's sample as well as the drum lanes', so project files carry it, and `adoptSamples` renames it on import with the rest. Anything else that comes to hold a sample id must be added to both.
- A drum lane can play an imported sample instead of its synthesized voice (`DrumTrack.sampleId`). The sample is played by `DrumCore` (`setSample`), so playback and export match; it is one channel, at most ten seconds, and skips the kit's colouring. `drumSamples.ts` decodes and caches by id; `useStudio` keeps the decoded samples for the worklet and for export.
- Samples live in this browser's sample store and travel only inside a saved project file. A lane whose sample is not on the device plays its synthesized voice and says so; never treat a missing sample as an error.
- A saved project file carries the audio of every sample its drum lanes use, as base64 in a top-level `samples` list beside `project` (`projectSamples.ts`). `handleExportProject` adds it with `embedSamples` and `handleImportProjectFile` takes it out with `adoptSamples` before the file reaches `importProject`; nothing else may do either. `sampleId` exists only on `drumState` lanes, which are project-wide, so a lane silent in the open scene still counts. Give `usedSampleIds` and the renaming in `adoptSamples` any new place a sample id is stored.
- A sample from a file is the same sample when its bytes are the same; the id is only what the lanes call it, and a file can say anything. Audio already in the store is not stored again (the lanes are pointed at the copy that is there), and an id already taken by different audio is never overwritten (the incoming sample gets a new id and the lanes follow).
- Embedded audio is untrusted and bounded: 4 MB a sample, 12 MB and 32 samples a file, an audio type or file name, valid base64. Anything else is dropped, the project still opens and the user is told how many were left out. The file is kept under the 20 MB an import accepts, which is also the limit in versions before this, and an older version reads only `project`, so it opens a new file with its samples missing. Do not raise the caps past that limit or move `samples` inside `project`.
- Import Kit puts several sample files on the drum lanes at once. `matchKit` reads only the file names, so every guess is shown in the dialog and can be changed; nothing is stored or changed until it is confirmed, and only files given a lane are stored. Add a naming convention by adding to `guess` in `kitImport.ts` and a name to its test.
- One file of audio ships with the app, `ui/public/waves.bin`: the sample engine's built-in sounds, from two CC0 libraries the owner agreed to on 2026-10-12. `docs/BUNDLED_AUDIO.md` records every source file and its licence, and `scripts/build-waves.mjs` makes the file; it is run by hand, never by a build. Adding a sound needs a licence read at its source, the owner's say-so, and an entry in all three. Check the pitch the script prints: three of the source files are named an octave below where they sound.
- Seven big instruments are built-in sounds that load on demand (2026-10-19, VCSL, `docs/BUNDLED_AUDIO.md`): two grand pianos, a pipe organ, a tenor sax and three FM keyboards. Each is its own file, `ui/public/sounds/<id>.bin`, in `waves.bin`'s format, named by `file` on its entry in `BUILT_IN_WAVES`; `loadBuiltInWave` fetches the file once the first time any of its sounds is asked for (a failed fetch is tried again at the next ask) and `loadLaneSample` is still the one place a lane's sound is turned into audio, so the studio and the share page get it without change. Until it arrives, or offline when it has not been fetched, the lane plays its oscillators, and the Osc page says so. `vite.config.ts` leaves `sounds/` out of the service worker's install list so nobody downloads them without using one; the worker's network-first rule keeps each after it is fetched. `waves.bin` holds only the small sounds, and a test says the two lists do not overlap. A new big instrument goes in `INSTRUMENTS` in the build script and in `BUILT_IN_WAVES` with a `file`. Not verified by ear.
- A built-in sound is named in `sample.wave` and wins over an imported `sample.id`. `loadLaneSample` in `builtInWaves.ts` is the one place that turns either into audio, for the studio and for the page a share link opens (the app's own sounds are there for a shared song; an imported sample is not). A name this version does not have plays the oscillators. A recorded instrument is several notes (`zones`), and a voice takes the one nearest its note when it is struck; a table of single cycles (`frame`) is played as an oscillator and stepped through at `sample.scan` a second with `sample.fade` of each step a crossfade.
- In the sample engine the first oscillator's level (`mixer.osc`) is the sample's level, and the second oscillator, when on, sounds beside the sample; that is how the D-50 model lays a recorded attack over a saw. The measuring helper gives a preset its built-in sound, so the preset tests measure what is heard.
- The Cymbal lane plays a recording for each kind of cymbal (`cymbalType`: crash, ride, bell, splash; `CYMBAL_TYPES`). The owner asked for this on 2026-10-12, having said the synthesized ones "sound nothing like cymbals" in any kit. The recordings are in `waves.bin` as `cymbal-<kind>`; `loadCymbals` fetches them once and `DrumCore.setCymbals` holds them, for the worklet (`useDrumAudio.setCymbals`), for export (`drumCymbals`) and for the page a share link opens. A cymbal is the same in every kit and is not coloured by it. Decay (`extra`) lays a fade over the recording and Tone a low-pass below the middle; both leave it untouched at their defaults' upper halves. `renderCrash` and the synthesized ride are still there and are what plays until the recordings have loaded, in kids mode, and in a unit test that hands the core none: do not delete them. An imported sample on the lane still comes first.
- The Recorded kit (kit id `recorded`, 2026-10-19, the owner asked for more bundled open-source drum sounds) plays a recording on every lane: `kit-<instrument>` in `waves.bin`, from VCSL (`docs/BUNDLED_AUDIO.md`), one hit each. It shares the cymbal's plumbing, which is now one list of recordings by name (`DrumRecordings`): `loadCymbals` returns the cymbals by kind and the kit's drums as `kit-<instrument>`, `DrumCore.setCymbals`, the `cymbals` worklet message, export's `drumCymbals` and the share page all carry that one list (their names say cymbal for history). `DrumCore.start` picks the recording only when `kitId` is `recorded`, so every other kit is bit-identical, and without the recordings loaded the kit is the clean-analog synthesized voice. Tune is playback rate, Decay (`extra`, the same fade as the cymbal) and Tone (a low-pass below the middle) leave a recording alone at the top and middle of the knob; the kit's own defaults have Decay at the top. The drum strip calls the last knob Decay on this kit (`RECORDING_EXTRA`) unless the lane has an imported sample. An imported sample still comes first. Not verified by ear.
- A drum lane can be other percussion, like `cymbalType` (2026-10-19): `DrumSettings.percType` (`PercType`; `PERC_CHOICES` in `engine/src/types.ts` says which lane has which: Clap is tambourine, shaker or cowbell, Snare a cross-stick, Low Tom (`snare2`) a conga, High Tom (`ride`) a bongo). The Voice menu in the drum strip sends `'default'` for the lane's own drum, which `sanitizeDrums` drops, and it keeps a choice only for a lane that has it, so an old project is unchanged in storage and hash. `DrumCore.start` plays `perc-<type>` in any kit when that recording is loaded (otherwise the lane's own sound), after an imported sample and before the kit's recording; it goes in the same list as the cymbals (`loadCymbals`, `PERC_TYPES`). Kit changes leave it, Reset clears it. The set is small on purpose: one extra instrument per lane that has a natural neighbour, and none for kick or the hats. Not verified by ear.
- No other kit's sound is a recording: no LinnDrum, DMX or TR-707 recordings are bundled. The owner decided this on 2026-10-09: no LinnDrum, DMX or TR-707 recordings were found that the project is clearly allowed to redistribute. The kits with those names in the kit menu are synthesized. Do not add recordings without the owner's say-so and a checked licence.
- `localService.exportProject()` / `importProject()` are the project file format (`format: 'discobot-project'`). Import goes through the same `restore()` sanitizing as a reload; never trust a file's contents. `exportProject()` is also what share links, published songs, sync and sharing are made from, so it must never hold audio: only the saved file gains its `samples`, in `useStudio`.
- The service worker serves hashed files under `assets/` cache-first and everything else network-first. Keep unhashed files (the page, `audio-worklet.js`) network-first, or an update would pair a new app with a stale worklet.

The rack's colours are named in `rack.css` (on `.rack-page`) by the job they do. A new control
picks from these names and never writes a colour out; if no name fits, add one there and to this
table. The names from before (`--amber`, `--ink`, `--legend`, `--dim` and the rest) are gone.

| Somewhere to type or choose | `--surface-field` |
| Behind lit figures (the tempo) | `--surface-display` |

| A name, a heading, what was typed | `--text` |
| A sentence, a word on a button | `--text-plain` |
| A label beside a control | `--text-label` |

| A word on anything lit | `--text-on` |
| On, open, or holding something: a step with a note, a pressed-in toggle, mute, the open scene, the open lane's edge, a lamp | `--on`, with `--on-bright` (its lighter edge, and its face under a pointer), `--on-glow` and `--lamp-off` |

| A drum lane | `--drum-kick`, `--drum-snare`, `--drum-clap`, `--drum-closed-hat`, `--drum-open-hat`, `--drum-low-tom`, `--drum-high-tom`, `--drum-cymbal`; a row carries `data-drum` and reads its own as `--drum-color` |

- Amber means two things only: this is on or holds something (`--on`), and this is a figure (`--value`). It is not for emphasis, headings, hover or focus. The two have the same colour today and are separate names so that either can change.
- Four states look different, and `state-looks.spec.ts` holds them apart. **Focus** is a 2px white ring 2px outside the control with a dark gap between (`.rack-page :is(...):focus-visible`), the same on everything; a new kind of focusable thing must be added to that rule's list. Where a ring outside would be cut off or lie under a neighbour (menu rows, song blocks, piano keys, the piano roll, the bar of units) the ring and gap are drawn inside the edge; add to that second list for anything in a clipped strip. **Hover** is a lighter edge (`--hover`), an underline where there is no edge, and a lighter face on something lit, the last only under `@media (hover: hover)` because a touch screen keeps a hover after a tap. **Selected** (a step the controls below act on) is a frame inside the step's own edge. **On** is an amber face with a dark word, for every toggle and every "this one is open"; the bar of units on a phone shows the unit on show as a lit line along the top of its switch, and keeps its lamps for what is playing.
- The focus ring's gap and the selected frame are both `box-shadow`, so a rule that gives a focusable thing a shadow of its own must say what it looks like focused as well (see `.step-cell.selected:focus-visible`), or focusing it would drop one of them.
- Each component's own stylesheet in `ui/src/components/` holds its whole look, on these names. `rack.css` does not restyle a component from outside: the only rules there that reach into one are the phone layout's (inside its media block) and the focus ring. A button anywhere is a `.rack-btn` (`.on` when lit, `.danger` when it deletes); do not give a component a button style of its own. The piano's keys are written out as a piano's white and black, and a knob's pointer is `--value` whatever `color` it was passed. Sizes and corners are part 3 of redesign C in `docs/DESIGN_REVIEW.md`. Kids mode has its own look and none of this applies to it.

## Conventions
- No comments in code unless explaining non-obvious logic
- `DrumState` always initialized with `createDefaultDrumState()` (never null)
- Engine types are single source of truth (`engine/src/types.ts`), UI re-exports via `ui/src/types.ts`
- All project mutations go through `localService`: a typed helper over `apply` (`docs/TYPED_STORE_PLAN.md`). Add an operation, its reducer, its `OP_META` row and a case in `storeEdits.test.ts` and `storeOps.test.ts`. Components do not write localStorage directly
- Sanitize anything read from storage in `projectSanitization.ts` before it reaches audio code
- The app must work fully with no account and with the API unreachable. Signed out, it makes no request to the API at all, with one exception the visitor asks for: opening a short link (`#s=code`) fetches that published song. A browser test checks both
- The API stores a username, password hash, recovery-code hash, join date and invite code, and nothing else: no email, no names, no IP addresses. Do not add personal data, analytics or logging of request contents
- Passwords, session tokens and recovery codes are stored only as hashes and never logged. PBKDF2 is capped at 100,000 iterations by Cloudflare
- The API is called with a bearer token, not cookies, and only answers origins in `ALLOWED_ORIGINS` (`server/wrangler.toml`)
- `server/` has no runtime dependencies and `wrangler` is run with `npx`, not installed, to keep the lockfile small
- Do not reintroduce Discord integration or a WebSocket transport

## Project Sync
- The browser copy is the working copy. The account holds a copy of each synced project with a revision number; a save names the revision it was based on and is refused (409) if the account has moved on.
- Nothing is merged and nothing is overwritten. A project changed in two browsers is kept twice: this browser's edits move to a new project (`syncFork`) and the account's version is downloaded under the original id.
- "Changed" is decided by `contentHash` of the project in `normalized()` form, never by the local revision number, which goes up on every write. Keep volatile fields out of the hash, or opening a project would upload it.
- Sync never infers a deletion from a project being absent, because lost browser storage must not empty the account. A delete reaches the account only through `projectSync.noteDeleted`.
- Signing in uploads nothing that was already in the browser; those projects are listed as "this browser only" until the user adds them. Projects made while signed in are the account's.
- Sync state is in `localStorage` under `discobot_sync_v1`, per username. Signed out, `startProjectSync` sends nothing.
- The server stores projects as sent and checks only size and shape. Whatever the browser downloads goes through `restore()` like a project file.
- Imported samples are not synced. `fileFor`, `contentHash`, the working copy, the library and kept versions hold a sample's id and never its audio; a test in `projectSamples.test.ts` checks each. Syncing samples needs file storage on the server.

## Working Together
- Two people work on one project in turns. There is no live connection and no merging: the owner shares a synced project by username, and the people it is shared with read and save the owner's copy under the same revision rule as everything else. This was chosen over live editing because a held-open connection is ruled out below; changing that is the owner's decision.
- A shared project stays in the owner's account. It is never copied into a member's account, and it only enters a member's browser when they open it from "Shared with you" (`projectSync.join`). Do not download someone else's project unasked.
- `createProjectSync` settles a project against a `Place`: this account (`/projects`) or the owner's copy (`/shared/<owner>/<id>`). `settle` is the one implementation of the rule for both; do not write a second.
- When both people changed a shared project at once, the one who syncs second keeps their edits as a project of their own (`syncFork`) and receives the other's version. Nothing is overwritten.
- When sharing ends (unshared, the project deleted, an account removed) the member's copy stays, as a project of this browser only. Deleting a shared project as a member only removes it here and leaves; only the owner's delete reaches the account.
- A server that has never heard of `/shared` answers 404. Sync reads that as "nothing is shared" and leaves every link alone; it must not read it as everything having been unshared. The accounts API is deployed by hand, so the site can be ahead of it.
- Sharing stores which account shared which project with which, and which account saved a project last (`project_shares`, `projects.updated_by`). No names, messages or activity beyond that.
- With anything shared, sync looks for changes every 20 seconds instead of every two minutes (`CHECK_SHARED_EVERY_MS`).

## Guest Instruments
- A guest is another creator's web page in a frame (`GuestModule`), listed in the project as `guests`. The protocol is `docs/GUEST_PROTOCOL.md`; `docs/guest-example.html` is a complete guest, and the browser tests run against it (served by `server/dev.ts` at `/__guest`). Change the three together.
- A guest's address must be https on another site (`guestUrl`). Discobot's own origin is refused: the frame is only kept apart from the app because it is a different site. Do not loosen this or the frame's `sandbox`.
- A guest is never loaded without the user's say-so for that site on this browser (`isTrustedOrigin`). Typing the address in counts; a guest that arrives in a shared or synced project asks first. This is the one place the app loads anything from another site.
- Messages are accepted only from the guest's own frame at its own origin, and everything in them is untrusted. The guest's `state` is opaque JSON, size-capped, never interpreted.
- Timing uses the computer's clock, which the frame and the app share. The guest plays early by a latency and `createGuestPlayer` holds its audio back by the same amount. The latency starts at `GUEST_LATENCY_MS` and is per guest: how long audio takes to cross from the frame differs between browsers, so a block that arrives after its time is still played at once (late, not silent), and after a run of them the latency is raised by what was missing and the guest is sent `hello` again with the new value.
- With guests connected the transport places its first beat further ahead (`guestLink.startLead`): the largest latency plus reaction time, or longer for a guest that has not been started since it loaded.
- A guest's settings belong to the scene, like a lane's steps. `guest.state` is the open scene's; `captureScene` copies it into `scene.guests` and `applyScene` copies it back, and `GuestModule` sends `setState` whenever the state changes from outside the guest (a scene opened, a song moving on, sync, a restore). A scene made before a guest was added holds nothing for it, and the guest carries on as it is.
- A guest is only asked for its settings every few seconds, so anything that leaves the open scene on the user's say-so must first `await guestLink.captureAll()` (see `sceneRequest`). Without it, a change made just before switching is recorded late, in the scene switched to. A scene change also always re-sends the scene's settings to the guest and starts a new epoch, even when the settings are unchanged.
- A guest's level and mute are per scene too (`scene.guestMix`). Its effect sends (`guest.sends`, absent when all are zero) are project-wide, like a lane's.
- A song export gives each guest its scenes' levels bar by bar (`guestBarGains`, passed to the renderer as a take's `gains`) and records every guest that any scene of the song plays. Never decide which guests to record, or how loud, from the open scene.
- Questions to a guest carry an epoch that goes up whenever it is sent settings. An answer from an earlier epoch describes settings the guest no longer has and is ignored; without that, a late answer would be saved into the wrong scene.
- `GuestModule` handles a message for every block of audio, many times a second. Nothing on that path may set React state; what the unit shows is refreshed on a timer.
- Do not use `window.confirm` for guest actions: a browser can be told to stop showing a page's dialogs, after which it silently answers no. The same goes for the rest of the app: ask with `ConfirmDialog` (`ui/src/rack/ConfirmDialog.tsx`).
- A guest cannot be rendered offline, so every audio export (`handleExportWav`) first plays the arrangement through and records each guest (`guestCapture`, fed from `GuestModule`), then mixes the recordings into the normal render as `guestTakes`, through the guest's sends. Recordings are placed by the guests' time stamps against the transport's first beat. For Loop WAV the pattern is played twice and the second pass kept, and the renderer lays that pass end to end. Stems give each guest a file of its own. MIDI leaves guests out.
- `handleExportWav` is the wrapper that sets `exportStatus` (working, then done) and refuses a second export while `exportingRef` is set; the work itself is `exportWav`. Export is a dialog (`ExportDialog`), not a menu: what (the open scene or the whole song), as what (audio, a seamless loop, stems, MIDI), a line saying how long the file will be, and the making of it reported in the dialog. Its Export button is disabled for audio while one is working; `Rack` shows the same message, which is what is left when the dialog is closed part way. A loop and stems are of one scene, so with the song chosen they are disabled. The renderer cannot report how far it has got, so the message says only that it is being made (Stems also name the file it is on). The files are still called Scene WAV, Loop WAV, Stems, Scene MIDI, Song WAV and Song MIDI in the messages and in Help. Each browser spec that exports has its own `exportAs(page, item)`, which takes one of those names, sets the dialog and closes it at once so the caller can wait for the download; `export-progress.spec.ts` holds the render open (it wraps `startRendering`) to look at the message and the disabled items.
- Two recordings of a guest do not land on the same sample: a take can sit a millisecond or two early, and more on a slow machine. A test that compares two guest exports must not measure a fixed window that ends where a sound begins; measure something that does not move with the take (`quietest` in `guests.spec.ts`). The check run on GitHub failed for exactly this while passing on a faster machine.
- A guest that lists `'input'` may take one voice: a lane (`synth:<id>`), the kit (`drums`) or one drum (`drum:<id>`), asked for 2026-10-19 for Axis Stack (`docs/GUEST_PROTOCOL.md`, "Input"). `guestInputs` (`services/guestInput.ts`) is the one record of it, outside React like the playhead: `useStudio` gives it the voices on offer and routes each to its guest's tap, `GuestModule` answers the guest and streams the voice, the scheduler reads each voice's lead, and the units read it through `useHandedTo`. One voice a guest and one guest a voice. A voice goes back to the mix at once when the guest asks, reloads or is removed, or the voice goes.
- Every audio lane (`createLane`) has a hand-over switch: its level feeds the ducker through a gate, and a second ducker feeds `toGuest`, which is silent until `handOver(tap)`; a drum lane's own send mixes have gates too. At rest every gate is 1 and the mix is what it was. `handOver` crossfades the gates down and `toGuest` up over `HAND_OVER_FADE`, so a handed voice leaves the mix and every send but is still ducked. A drum handed over alone is played by a drum processor of its own (`useDrumAudio`'s players), so the rest of the kit stays in the mix; a choke between it and the kit's other drums is lost while it is.
- A handed voice is scheduled early by its lead (`leadSeconds`), so the guest's return lands on the beat; the transport reaches that much further ahead (`reach`, `reachSeconds`), and `showStep` holds each step light back to when its step is heard, since otherwise every light would lead the beat while anything is handed over. Nothing changes while nothing is: the lead and the reach are 0. Live notes are not early and come back late by the lead.
- An export's play-through records which voices are handed over at each bar (`handedByBarRef`), and `leaveOutHanded` takes them out of the render (a song bar by bar, a scene throughout); the guest's take has them. Without a play-through (the guest silent) they are left out as well, as they are silent live.
- The example guest takes a voice only with `?input=1` in its address, and then rings no bell and plays the voice back unchanged; without it, it is as it was. `guest-input.spec.ts` uses it.
- `FEATURED_GUESTS` lists instruments offered by name in the Add Guest dialog. Only add one with its creator's permission. Pocket Mouse was added on 2026-10-12 because the owner asked for it; it is by the creator of the other three. Axis Stack (an XY effects pad, by the same creator) was added on 2026-10-19 at the owner's request, with a prompt its creator wrote for Discobot to support it. Tape Loop Deck is on hold and off the list by the owner's decision (2026-10-10); it can still be added by its address. Do not put it back without asking.

## Kids Mode
- Kids mode is a page of its own at `#kids`, for a child too young to read. `App` chooses it before `useStudio` runs, so the project store is never opened and nothing there can change, delete, share or publish a project. Keep it that way: do not import `localService`, `account` or anything that reaches them into `ui/src/kids/`. Going in (Project menu) and coming out both reload the page. The three-second hold is the only way out, so kids mode lasts for the whole visit to a tab (`keepKidsMode`, a flag in `sessionStorage`): going in replaces the address and adds no page to go back to, and an address changed while in kids mode is put back. Only `leaveKidsMode` clears it. The page cannot stop Back from leaving the site altogether.
- There are two activities, each a screen, and one is shown at a time: the pads, and the beat grid. The way between them is two drawings at the top left (`SCREENS` in `KidsPage.tsx`), not words. Play, the speed and the level are shared, and both keep playing whichever screen is open.
- What a child makes is kept under its own key (`discobot_kids_v1`) and read back through `sanitizeKids`: `notes`, two bars of eighth notes for each pad; `beat`, one bar of eighth notes for each row of the grid; and the sound, the speed and the screen last open. It is not a project and cannot be opened as one; whether it should be is the owner's to decide.
- The key is still `_v1` because what the first version stored still loads: `sanitizeKids` fills anything missing with its empty value. A stored tune names a pad and a sound by its place in `KIDS_PADS` and `KIDS_SOUNDS`, so add to the end of those lists and never reorder them. Where a pad sits on the screen is `KIDS_PAD_ORDER`. A test holds the first nine pads and four sounds in place.
- Nothing on the page needs reading: no text fields, menus, dialogs, sliders or links, and a browser test checks there are none. The one line of text, "Hold to leave", is for the adult, and that button only works held for `KIDS_LEAVE_HOLD_MS`. New pictures are emoji or SVG drawn in the component; nothing is bundled for them.
- A pad acts on `pointerdown`, not on click, so it sounds as it is touched. While the loop plays, a tap is also kept on the nearest step (`stepNearest`), and the loop skips that step once because the tap has already played it.
- The note pads are eight notes of one five-note scale, so no two clash, and there are four drum pads. The level is fixed at `KIDS_VOLUME` and there is no volume control. The six sounds were set by reasoning, not by ear.
- Each row of the beat grid is the drum of one pad (`KIDS_BEAT_ROWS`), with that pad's picture and colour. `padSounds` is the one place that says whether a pad plays on a step, from the taps and the grid together, and both the scheduler and the lights use it; that is why a drum in both is one hit, not two. A hole sounds as it is filled, not as it is emptied. The sponge wipes only the screen it is pressed on.
- The grid's markup is one instrument after another, a picture then eight holes. CSS alone turns it: instruments are rows on a wide screen and columns on a tall one (`orientation: portrait`), where eight holes across would be too small to touch. The pads are three across on a tall screen and four across otherwise.
- The lights follow the playhead rule. The scheduler writes the step to `playhead` under the lane `'kids'`, and one layout effect in `KidsPage` switches `now` on the dots and the grid's holes and `lit` on the pads, found by `data-step`, `data-beat` and `data-pad`. Those two classes must not appear in a `className`, and the effect has no dependency list on purpose.
- A first visit starts with a drum and a clap in the beat grid and no tune (`starterKids`).
- Kids mode makes no request to the accounts API or to any other site, signed in or not. A browser test checks it.

## Published Songs
- Publishing stores a slimmed copy of a project on the server behind a ten-character code. It is always an explicit button press, never a side effect of sharing or syncing.
- Reading a song needs no account and returns the title, the publisher's username and the project. Never add anything else about the publisher to that response.
- Publishing the same project again replaces the copy and keeps the code. Unpublishing deletes the row; the site owner can unpublish any song.
- A published song is untrusted like any project file: `SharedSongPage` reads it through `readProjectFile`.
- Each person has a page of the songs they have published, at `#u=name` (`UserSongsPage`). The owner decided on 2026-10-10 that this is all there is: no page of everyone's songs, no browsing, no search and no list of people. Do not add one without asking. The page is reached by its link, from the publisher's name on a song's page, or from Share Link, where a signed-in user copies the link to their own.
- `GET /users/<name>/songs` needs no account and answers `{ author, songs: [{ code, title, updatedAt }] }`, newest first. Never add anything else to it: no project ids, join date, counts or anything about projects that are not published.
- A username nobody has, one with nothing published and text that could not be a username all get the same `{ songs: [] }` with status 200, from one query, and `author` is only there when there are songs. Keep it so: the route must not tell anyone which usernames exist.
- Opening `#u=name` is the second request a signed-out visitor can cause, after opening a short link, and like it is one the visitor asked for. It is sent without the session token even when signed in. A link that could not name a username sends nothing. `user-songs.spec.ts` checks both.
- The list is other people's text: `readUserSongs` keeps only codes, titles and times of the right shape, caps the titles and the count, and shows the name that was asked for unless the server returns the same name in other capitals. Titles are rendered as text.
- `App` chooses the page before `useStudio` runs, as it does for kids mode, and moving between it and any other page reloads. The songs on it are plain links to `#s=code`.
- A server from before the page existed answers 404 for the route, and the page then says such pages are not available yet. The accounts API is deployed by hand, so the site can be ahead of it; a server that cannot be reached gets a different message and a Try Again button.

- Names: a drum has one name (`DRUM_NAMES` in `services/drumKits.ts`, which the grid, the mixer, the MIDI panel and the parameter names all read; `DRUM_ROWS` beside it is the order the grid and the mixer show them in: Kick, Snare, Clap, Closed Hat, Open Hat, Low Tom, High Tom, Cymbal), shown whole on the grid, in its hint, to a screen reader and in Import Kit. The grid's name column is 64px wide (`--side` is that plus mute and solo, so it is 120px) and wraps on a phone. A knob's visible label may be shortened only where it cannot fit, as the lane's "Reso", and then carries the whole word as its hint; its accessible name is always the whole word. A lane says its model's name (`Generic`) under its own name. `matching-names.spec.ts` checks that none of these is cut off.
- `Menu` takes `groups` (lists of `MenuItem`), draws a `role="separator"` line between them (not a tab stop) and an item's `danger` flag draws it in the danger colour. A row's `title` is its hover hint and, on a narrow screen, its second line (a `::after` reading `data-hint`, so a row's text and name stay its label only; tests that read the menu's text depend on that). The Project menu is projects; in and out; extras; Reset All alone.
- The word beside the project's name on the transport (`SaveState`, wording in `services/saveState.ts`) says only what the app knows: `localService.saveState()` (an edit waiting for the 300 ms write, written, a refused write, or paused because another tab has the project) and, signed in, `projectSync.status()`. "In account" needs the project in the account's list and a sync pass that began after the latest write; an edit written since then is only "Saved". It is a `role="status"` of fixed width. On a narrow screen it is not on the bar but spelled out in the top bar's sheet and in the Projects dialog; the sheet is put away before that dialog opens, so only one is ever rendered.

## Working Rules for Agents
- Skills for this repository are in `.claude/skills/`: `add-project-field` (anything stored), `ship-change` (checks, commits, pull requests) and `scripted-edits` (editing on Windows). Read the one that fits before starting.
- `docs/HANDOFF.md`, when it exists, says where unfinished work stopped. Read it first and delete it when that work is merged. Questions it leaves for the owner go to the end of `docs/ROADMAP.md` first.
- Reproduce a reported bug before fixing it, and see it fixed the same way afterwards. If it cannot be reproduced, say so; do not report a guess as a fix.
- Find another program's real definitions before translating its files or talking to it (its source, its parameter table). Do not infer units from field names.
- Anything bundled with the app must be something the project may redistribute. Do not add samples, fonts or data whose licence has not been checked.
- The project pays for nothing (the owner, 2026-10-12). Never plan, propose or build on anything that costs money, asks for a payment card or bills by use, and never describe work as waiting on a payment. Syncing samples was designed on Cloudflare R2, which asks for a card, so it is not planned.
- Changing which outside service a workflow or the app sends data to, or adding a secret, is the owner's decision. Ask first.
- Sound cannot be verified by tests. Say "not verified by ear" when that is the case.
- Pictures of the app, for a design review or to see what a change looks like, are taken on GitHub and never on this machine. `ui/test/browser/design-shots.spec.ts` walks the app at both widths and saves a screenshot of each screen into `test-results/`; it checks nothing and is skipped unless `DESIGN_SHOTS` is set, which `ci.yml` does only for a pull request whose branch name contains `design-review`. The pictures are then in that run's `test-results-chromium` and `test-results-mobile-chromium` artifacts (`gh run download`), each put together by the `results` job from the four machines that ran that width (the `browser` job is split with `--shard`; while it runs, a machine's own results are `test-results-<width>-<1 to 4>`), kept for a week, with a `skipped.txt` beside them listing any screen that could not be reached. Do not commit the pictures. Add a screen to that spec when the app gains one; `docs/DESIGN_REVIEW.md` lists what each picture is.
